# Migration: add `go_subject` and `go_sample`

## Why

The data model is being extended upwards so the full provenance chain is
modelled explicitly:

```
Project → Subject → Sample → Assay → File
```

`types.Assay.SampleID` (int64) has always been documented as a foreign key to a
*future* `Sample`. This migration adds the two missing tables:

| table | Go type | meaning |
| --- | --- | --- |
| `go_subject` | `types.Subject` | donor / individual (e.g. `Mouse-001`) |
| `go_sample` | `types.Sample` | one biological sample taken from a subject |

`go_assay.sample_id` now resolves to `go_sample.id`.

## Naming: `sample_id` is the business number, `id` is the PK

Both tables follow the `go_file` convention (`File.FileID` string business
number + `ID` int64 PK):

| column | notes |
| --- | --- |
| `go_subject.id` | int64 PK, generated by `utils.GenerateID()` |
| `go_subject.subject_id` | varchar(255), **unique** business number (`Mouse-001`) |
| `go_sample.id` | int64 PK, generated by `utils.GenerateID()` |
| `go_sample.sample_id` | varchar(255), **unique** business number |
| `go_sample.subject_id` | int64 FK → `go_subject.id` (indexed) |

> Superseded: `go_subject.subject_id` was later renamed to
> `go_subject.subject_name` (it is a business *name*, not an id) — see
> `migrations/2026-09-23-subject-name-rename/`. `go_sample.subject_id` keeps its
> name because it really is an id (FK → `go_subject.id`).

> Do not confuse `go_sample.sample_id` (business number) with
> `go_assay.sample_id` (int64 FK to `go_sample.id`).

The Python-era `t_samples` table is unrelated and untouched.

## Applying

The Go binary runs `AutoMigrate` for both types on startup
(`internal/container/container.go`), so a fresh/upgraded deployment normally
needs nothing else. The accompanying `mysql.sql` / `postgres.sql` /
`sqlite.sql` only exist for environments where DDL is applied by hand; every
statement is idempotent.

Two steps cannot be automated and are the operator's responsibility:

1. Backfilling legacy sample data into `go_subject` / `go_sample` (the old
   Python `t_samples` rows have no subject, so a subject must be invented or the
   rows must be skipped).
2. Re-pointing `go_assay.sample_id` at the new `go_sample.id` values.

Both are intentionally out of scope: until they are done, `go_assay.sample_id`
simply references a row that does not exist yet.

## No new HTTP surface is versioned by this migration

The new endpoints (`/data/subject/*`, `/data/sample/*`, plus
`/data/dataset-assay/get-by-assay`) are
additive; nothing existing changed shape.

> The `/data/assay-file/list-by-assay` endpoint that shipped with this migration
> was replaced by `/data/file/list-by-assay` when `go_assay_file` was folded into
> `go_file` — see `migrations/2026-09-23-file-assay-binding/`.
